## 1-1. 프로젝트 개요

### 프로젝트 주제
한국어 영화 리뷰 텍스트를 4개의 감성 레이블(0: 강한 부정, 1: 약한 부정, 2: 약한 긍정, 3: 강한 긍정)로 분류하는 감성 분석 모델 개발

### 프로젝트 구현 내용 및 컨셉
- **핵심 문제**: 레이블 불균형 문제 해결 (0: 40.79%, 1: 9.73%, 2: 35.55%, 3: 13.93%)
- **접근 방법**: 
  - LLM 기반 데이터 전처리 시도 (emoji 변환, 맞춤법 교정, 노이즈 제거)
  - Stratified K-Fold 5를 통한 불균형 데이터 학습
  - 평가지표: ACC 대신 F1 Macro Score 채택 (앙상블 효과 극대화)
  - 모델 고정 상황에서 전처리 최적화를 통한 OOV 최소화 전략

### 활용 장비 및 재료

**컴퓨팅 환경:**

| 구분 | CPU | GPU | RAM | 비고 |
|------|-----|-----|-----|------|
| 서버1 | 제온골드 5220 | V100 32G | 88G | Kubernetes 클러스터 |
| 서버2 | 9600x | RX9060xt 8G | 96G | Ubuntu 22.04, Docker vLLM |
| 로컬 | Apple M4 | M4 GPU 10코어 | 32G | lmstudio+mlx |

**개발 환경:**
- 네트워크: OpenVPN + ASUS Router VPN Fusion
- Terminal: Terminus
- IDE: Cursor
- LLM Coding Assist: Claude 4 Sonnet + Gemini 2.5 Pro
- Python: 3.11 (uv 패키지 매니저)

### 프로젝트 구조 및 데이터셋 구조

**데이터셋 특징:**
- 총 279,650개 샘플 (학습 데이터)
- 레이블 불균형: 소수 클래스(약한 부정) 9.73% vs 다수 클래스(강한 부정) 40.79%
- 노이즈 문제: 오탈자, 무의미한 문자열(예: 'ㅇ렇ㄹㄹㄹ'), 다수의 emoji 포함

- Confusion Matrix 분석을 통한 예측 순서 조율

## 1-3. 프로젝트 수행 결과

### 탐색적 분석 및 전처리

**데이터 분석:**
- 총 279,650개 리뷰 데이터
- 클래스 불균형 심각: 약한 부정(1) 클래스가 9.73%로 가장 적음
- 인터넷 리뷰 특성상 오탈자, 이모지, 무의미한 반복 문자 다수 포함

**전처리 전략:**
파인튜닝 불가 상황 → 전처리 중요성 극대화 → OOV(Out-Of-Vocabulary) 최소화 목표

1. **Emoji 처리**: 감정 정보를 담은 이모지를 해당 단어로 변환하여 정보 보존
2. **맞춤법 교정**: LLM을 활용한 의도 파악 기반 오탈자 수정
3. **노이즈 제거**: LLM as a Judge 방식으로 무의미한 리뷰 필터링

### 모델 개요

**BERT 기반 피쳐 추출:**
- 사용 모델: klue/bert-base
- 효율화: 런타임마다 BERT 추론 대신 피쳐를 PT 파일로 저장 후 재사용
- 고려했으나 미적용 모델: klue/roberta-base, kykim/bert-kor-base, beomi/kcbert-base, monologg/koelectra-base-v3-discriminator

**분류 모델:**
1. **ResNet 기반 MLP**: 깊은 층을 쌓기 위한 Residual Connection 적용
2. **XGBoost**: 다중 클래스 분류에 강점
3. **LightGBM**: 빠른 학습 속도

### 모델 선정 및 분석

**모델 선정 과정:**
- Grid Search: 레이어 수, 히든 사이즈 탐색
- 하이퍼파라미터 최적화: 학습률, Weight Decay, Dropout
- Weighted Loss 적용: 클래스 불균형 완화 시도

**최종 모델 구성:**
1. XGBoost 모델
2. LightGBM 모델  
3. ResNet 기반 MLP 모델

### 모델 평가 및 개선

**개별 모델 성능:**
- XGBoost: ACC 0.736 (최우수)
- LightGBM: ACC 0.733
- ResNet MLP: ACC 0.71

**앙상블 전략:**
- 하드보팅 방식 적용
- Confusion Matrix 분석 결과: 다수 클래스가 소수 클래스를 과다 흡수하는 패턴 발견
- Weighted Loss로 개선 시도했으나 효과 제한적


### 시연 결과

**최종 모델 성능:**
- **최종 ACC: 0.74** (앙상블 적용)
- 개별 모델 대비 +0.003~0.005 성능 향상

**성능 향상 요인:**
1. BERT 피쳐 캐싱으로 인한 효율적인 실험 반복
2. 3개 이질적 모델의 하드보팅 앙상블
3. Stratified K-Fold를 통한 불균형 데이터 학습

## 1-5. 자체 평가 의견 및 회고

### 잘한 점들

1. **효율적인 피쳐 관리**: BERT 피쳐를 PT 파일로 저장하여 반복 실험 시간 대폭 단축 (22만개 데이터에 대한 반복 추론 방지)

2. **적절한 평가지표 선택**: 대회는 ACC 기준이었으나, 데이터 불균형 상황을 고려해 F1 Macro Score를 채택하여 앙상블 효과 극대화

3. **다양한 컴퓨팅 환경 활용**: V100 서버의 한계를 개인 하드웨어(RX9060XT, M4 Mac)로 보완하여 3,200개 전처리 데이터 확보

4. **uv 패키지 매니저 도입**: pip의 빌드 과정 불안정성 문제를 uv로 해결

### 시도했으나 잘 되지 않았던 것들

**1. LLM 기반 전처리 실패**

**V100 호환성 이슈:**
- Compute Capability 7.0의 제약으로 최신 기능 미지원
  - sglang: CC 7.5 이상 필요
  - FlashAttention2: 미지원
  - FP8 가속: CC 8.9 이상 필요
- BF16→FP16 변환 시 토큰 생성 불안정 (무한루프, 언어 혼용)

**양자화 문제:**
- GPTQ INT4: 답변 품질 저하 (한글-다른 언어 혼재)
- GPTQ INT8: Exaone 4B 소형 모델만 가능 → 긴 문맥 이해 실패, 과도한 삭제
- Qwen 계열: 긴 문맥에서 중국어 비중 증가, 파싱 오류
- GGUF (llama.cpp): 배치 처리 불가 → 600시간 소요 예상으로 포기

**Function Call 방식:**
- Call fail 빈번 발생으로 실용성 없음

**직접 양자화 시도:**
- CPU 양자화와 GPU 로드 방식 불일치로 vLLM 활용 실패
- Hugging Face 업로드 완료했으나 실제 사용 불가

**ROCm 환경 구축:**
- RX9060XT + Ubuntu 22.04 조합으로 진행
- WSL에서의 ROCm 성능 문제로 네이티브 우분투 설치
- V100 대비 비등한 성능으로 3,200개 데이터 처리 성공
- 그러나 27만개 처리에는 시간 부족

**결과**: LLM 전처리는 인프라 제약으로 소규모(3,200개)만 적용, 전체 데이터셋에는 미적용

**2. 소프트보팅 앙상블 미시도**
- 서버 HDD 용량 문제로 모델 weight 미저장
- 레이블 결과만 저장하여 하드보팅만 가능
- 소프트보팅 시 추가 성능 향상 가능성 있었으나 미검증

**3. 회귀 기반 임계값 방식 미시도**
- 0부터 연속값으로 예측 후 데이터셋 클래스 비율에 맞춰 퍼센타일 기반 임계값 설정
- 시간 제약으로 실험 불가

### 아쉬웠던 점들

1. **인프라 트러블슈팅 시간 과다**: 프로젝트 2일 중 대부분을 V100 호환성 문제 해결에 소모
   - vLLM 엔진 버전별 호환성 (V0/V1/V2)
   - 양자화 포맷과 하드웨어 조합 테스트
   - FlashAttention2, CUDA Graph 등 가속 기능 호환성
   - → llama.cpp로 갔다면 시간 절약 가능했을 것

2. **전처리 완료 실패**: 계획한 LLM 기반 대규모 전처리를 완수하지 못함 (3,200/270,000)

3. **피쳐 엔지니어링 부족**: Random Forest 기반 피쳐 중요도 분석 계획했으나 시간 부족으로 스킵

4. **Weighted Loss 효과 미흡**: 클래스 불균형 문제가 Confusion Matrix에서 여전히 명확 (다수 클래스의 소수 클래스 과다 흡수)

5. **다양한 BERT 모델 미비교**: klue/bert-base만 사용, 다른 4개 모델과의 성능 비교 및 앙상블 미실시

6. **서버 저장공간 관리 실패**: Weight 저장 불가로 소프트보팅 기회 상실

### 프로젝트를 통해 배운 점 또는 시사점

1. **하드웨어 제약사항의 중요성**: 
   - Compute Capability, 지원 데이터타입(FP16/BF16/FP8), 메모리 대역폭 등이 실제 프로젝트 가능성을 좌우
   - 최신 모델과 레거시 하드웨어의 호환성 갭이 생각보다 큼

2. **도구 선택의 전략적 중요성**:
   - vLLM의 배치 처리 vs llama.cpp의 호환성 트레이드오프
   - 프로젝트 기한 내 "작동하는 것"이 "최적인 것"보다 우선

3. **패키지 매니저의 중요성**: 
   - pip의 임시파일 관리 문제를 uv로 해결
   - 빌드 안정성이 실험 반복 속도에 직접 영향

4. **효율적 실험 설계**:
   - BERT 피쳐 캐싱이 프로젝트 성공의 핵심 요인
   - 반복 실험이 필요한 부분의 사전 계산/저장 전략 필수

5. **평가지표 선택의 철학**:
   - 대회 기준(ACC)과 실제 목적(불균형 데이터 성능)의 괴리
   - 최종 목표에 부합하는 지표 선택이 모델 개선 방향 결정

6. **앙상블의 실용성**:
   - 짧은 시간에 단일 모델 최적화보다 여러 모델 조합이 효과적
   - 하드보팅만으로도 +5%p 향상 (0.71-0.73 → 0.76)

7. **계획 대비 실행의 현실**:
   - 야심찬 LLM 전처리 계획 vs 실제 인프라 한계
   - 빠른 pivot과 대안 수립 능력의 중요성 (RX9060XT, M4 Mac 투입)
